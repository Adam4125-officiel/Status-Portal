Update preferences

Prereleases (-rc.N) are cut for testing before being confirmed working. Pick unstable only if you’re happy to be the one finding the problems.

Turn this off to stop the portal making any periodic outbound call — “Check now” still works on demand. This is the same switch as the Update check task on Scheduled tasks, where you can also change how often it runs and see when it last did.

Rollback points (application code)

Each update backs up the files it replaces, under instance/update_backups/. These hold code, not data — rolling one back undoes an update and leaves your services, incidents and settings exactly as they are. Restore one from a shell: python update.py rollback --to <name>. Deliberately not a button here — the case it exists for is a portal that won’t start.

Database backup and restore

A zipped, consistent snapshot of instance/portal.db, taken right now — worth keeping an off-box copy of, and worth taking before poking at anything by hand.

Download a backup

Restore one

Upload a backup zip produced by the button above (or the portal.db from inside one) to replace your current database with it. This is data, not code — the opposite of the rollback points above, and neither can restore the other.

Everything currently in the portal — services, incidents, maintenance windows, settings, reports, the admin password and any 2FA enrolment — is replaced by whatever the backup holds. Your current database is saved to instance/db_backups/ first, and the file is checked for being a real Status Portal database before anything is touched. The portal restarts afterwards.

A .zip from the backup button, or a bare .db.
