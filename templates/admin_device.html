Display device

A small, read-only summary of this portal for a dedicated status display — such as a Status-ESP on a GeekMagic SmallTV — that asks for it over your home network every so often. It is a separate, much smaller answer than the public status page, and it is protected by a key because it can include things the public pages hide.

Display device API

Off by default. While it is off, or before a key exists, the address answers “not found” to everyone — exactly like a portal that never had this feature. Switching it on for the first time generates a key for you.

Setting up Status-ESP

In the display's web interface, on its Status-Portal tab:

  1. Portal address: this server's address on your home network and the port the portal listens on, for example http://192.168.1.10:{{ port }}. It has to be plain http:// — the display cannot do HTTPS, so a public https:// hostname in front of the portal will not work for it. Use the address you would type on a phone at home.
  2. API key: the key above.
  3. What to show: tick the parts you want on the display. It asks the portal only for those, which keeps each answer small.

To check it from a computer on the same network: 

curl -H "X-Api-Key: YOUR_KEY" \
  "http://192.168.1.10:{{ port }}/api/device/summary?sections=services,incidents"

What the display can see

/api/device/summary takes an optional sections list; leave it out for the five sections below, vms excepted (it is only sent when named). Every list is short, and every name and message is cut to fit.

SectionCarries
servicesHow many services are in each state, and the worst few that are not operational. A service you excluded from the overall status is excluded here too. With services=all: every service, with the latency of its last check.
incidentsHow many incidents are open, and the newest few.
maintenanceMaintenance in progress, then the soonest upcoming.
announcementsAnnouncements showing right now — never a scheduled or expired one.
resourcesCPU, memory, network and the fullest few disks. With resources=all: up to eight disks and the NVIDIA GPUs (load, memory, temperature) for a display that pages through them. With jellyfin=1 the answer also says what Jellyfin is doing (transcodes and running tasks), whichever sections are asked for.
vmsThe Hyper-V virtual machines the portal detects: how many, how many are running, and up to ten (by name) with their state and uptime. Only sent when you name it (sections=vms, alone or with others): leaving sections out still returns the five above, so a display that predates it is never handed more than it expected. An empty list when the portal is not on a Hyper-V host.
Resources and VMs are included even where the public pages hide them. The “Public page: also show…” switches decide what visitors see; the key decides what your own display sees. Nothing is reachable without the key.

Fuller answers for a server (detail=full)

A display needs short strings and short lists; a server that shows this status to people (the Jelly Portal plugin for Jellyfin) has room for more. It asks the same address with detail=full added. Only sent when you ask for it: without it the answer is exactly what a display gets, byte for byte, and any other value (detail=, detail=compact, a typo) is treated as if the parameter were not there.

WhereWhat changes with detail=full
HeaderThe site name is cut at {{ full.site_bytes }} bytes instead of {{ compact.site_bytes }}, and the answer says "detail": "full" right after overall. That is how a caller tells a portal that honoured the parameter from an older one that ignored it.
servicesUp to {{ full.service_items }} services listed (with or without services=all) instead of {{ compact.service_items }} or {{ compact.all_service_items }}; names cut at {{ full.service_name_bytes }} bytes instead of {{ compact.service_name_bytes }}. Same keys, and the same rule about services you excluded from the overall status.
incidentsUp to {{ full.incident_items }} open incidents instead of {{ compact.incident_items }}, titles cut at {{ full.incident_title_bytes }} bytes. Each incident also carries service_names: the full names of the services it covers, as a list (empty when it covers none), so a name containing a comma stays one name.
maintenanceUp to {{ full.maintenance_items }} windows instead of {{ compact.maintenance_items }}, titles cut at {{ full.maintenance_title_bytes }} bytes. Each window also carries service_names (as above) and description: its description as one line, up to {{ full.maintenance_description_bytes }} bytes.
announcementsUp to {{ full.announcement_items }} announcements instead of {{ compact.announcement_items }}, titles cut at {{ full.announcement_title_bytes }} bytes and text at {{ full.announcement_text_bytes }}, still one plain line. A scheduled or expired announcement is never sent.
Everything elseresources, vms and jellyfin are not affected, and a plugin that shows this to Jellyfin users should never ask for them: they describe the machine, and the key is what lets a display see them.
An older portal does not know the parameter and ignores it, answering the compact way without the detail key. The name lists hold at most {{ full.service_list_items }} names each, cut like the names in services, so a name in a list compares equal to the same service's name there. Nothing here costs an extra database query. A typical full answer is a few kilobytes; for the plugin's request it can never exceed {{ max_bytes_full_sections }} bytes, and the largest answer the endpoint can ever give (every section, every option and detail=full) is {{ max_bytes_full }}.
